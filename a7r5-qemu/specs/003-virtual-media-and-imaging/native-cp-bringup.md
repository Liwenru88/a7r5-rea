## 完整初始化请求捕获

旧日志只保留前 80 字节。本轮新增仅显式开启的 `A7R5_CP_INIT_CAPTURE=1` 观察器，在固定来源、长度和头部全部匹配后，将原请求复制到独立预留 RAM：`0x41ea00000/0x4000`，最多四个 4096 字节槽。

每槽包含序号、长度、来源/目标、FNV-1a64、原始 2400 字节及最后提交标识。完整复制后才提交。主机通过 QMP 暂停、导出并独立检查，保存原始字节及 SHA-256。它不使用画面串口传输，不增加 CP 回复，不改变原消息内容或所有权。协议失败后没有追加客体命令。

本轮现场：`runs/native-media-zfu_qwdk/`。`cp-init-capture.json` 只确认捕获；`result.json` 保留 `0x4073` 被拒绝的失败状态。QMP 退出 0。没有用捕获成功覆盖应用失败。

## CP 本体的通知路径

静态核对原始 CP：

- `0x340884` 是带 `FW: SET_NOTIFY_MODE` 字符串的处理器。读取请求 `+8` 的模式，使用 `0x157aa10+0x20` 保存状态。
- 模式 1 路径生成 12 字节完成体，状态 `0xf000`；发送调用为 `0x898210`。
- 随后调用 `0xab42bc`，原程序构造内部命令 `0xd018`，涉及 `0x90030001` 与成像端点 `0x90040193`。
- 由此不能把 ACK 当作完整参数通知。`0x2040` 的实际生产者、所需运行状态及其全部字段仍待闭合。

反汇编与完整请求逐字清单在 `logs/native-cp-20261022/`。清单刻意标记字段语义尚未验证；没有将请求直接复制成通知或注入全零通知。

## 四核实验板及限制

`source/qemu/a7r5-cp-boot.c` 仅加入新机器类型，不替换默认 QEMU：

- 四个 Cortex-A35，AArch32、EL1 起始上下文，各核 MPIDR 低位 0..3。
- 128 MiB 低地址 RAM；无物理磁盘、网卡、USB 或主机目录共享。
- QEMU 标准 GICv2，`0xf13a1000/0xf13a2000`。288 IRQ 为实验配置，未证明等同机身。
- PL011 轮询 UART `0xf1000000`；RX IRQ 未接线。
- 沿用既有 `sony-hwtimer`，原 CP 接受通道 0..8。4 MHz 模型频率、IRQ 输入 `200+n` 及全部寄存器行为未完成 CP 实机等价核验，不能用无异常代替正确性证明。

没有启用 AP 实验的全外设返回全一占位总线，没有写同步计数放行，也没有在 CP 中跳过初始化或修改 ready 字段。QEMU 仍默认拒绝的 macOS 沙箱，控制仅走本实例 Unix QMP，结束后退出本实例。

当前不能将调度器空闲认定为完整启动：AP 与独立 CP 实验环境未连接，共享缓冲区、消息所有权、中断/唤醒及原厂服务注册仍待证明。实际芯片的 CPU 分工和 AP/CP 启动关系也不能由这个实验板反推。

最终现场为 `runs/native-cp-boot-if4rrjis/`：请求观察 2000ms，实际约 2023ms；四核存在，记录 6 次 IRQ 进入，未记录数据异常，CPU0 为 `PC=0x5cc278`。`0x157aa10` 通知上下文仍为零；未收到 AP 初始化，因此不能据此认定 CP 服务正常。启动观察已关闭 semihosting，保留原程序自身的 SVC 语义。

矩阵最终现场为 `runs/native-cp-matrix-0m9c08at/`：3096 组通过，半主机退出码 0。`exit.json` 中原监督器的 `not-started` 表示未执行 QMP 关闭分支，不是进程从未启动；进程 PID、命令和 `cp-result.json` 的 `completion=semihosting_exit` 一并留存。

## 重现入口

在项目目录使用 `.venv/bin/python -B`：

```sh
# 固定归档提取、构建入口、真实 QEMU 矩阵窗口验收
.venv/bin/python -B tools/cp_native_probe.py

# 构建独立实验板；不更新 bin/ 或 runtime/manifest.json
.venv/bin/python -B tools/build-cp-qemu.py

# 使用日志中记录的 CP 与 QEMU 候选目录；不是任意固件执行入口
.venv/bin/python -B tools/cp_native_probe.py \
  --candidate build/cp-native-xdlzcywd \
  --boot-trace --cp-qemu build/cp-qemu-dknqffld --observe-ms 2000
```

`--resume` 仅重建本工具创建的独立 QEMU 目录，保存旧板源码、二进制和收据。新二进制以摘要命名，不替换已保留版本。所有材料身份不符立即拒绝；不要为兼容未知 CP 放宽摘要门槛。

## 验收和下一步

本轮相关 Python 契约测试与宿主 C ASan/UBSan 检查通过，详情见相邻日志和本轮汇总收据。USB/SSH/相机/卡均未访问；没有重跑或改动默认 Qt 菜单。

保留了入口编译、音频后端、Thumb semihosting 和对齐/异常入口诊断失败日志。旧没有异常向量的试验入口曾重复输出开始标识，已由完整输出校验拒绝；新增输出上限及异常入口后，原始指令试验才通过。C 所有权回归首次遗漏必要环境开关失败，正确开启后通过，失败未覆盖。

后续完成标准按顺序推进：

1. 核对 CP 原厂任务/消息队列及启动阶段；分别证明调度、计时器、中断和服务就绪。
2. 查清原厂 AP/CP 消息传输与共享内存契约，建立不改变原消息语义的连接；不预设为两个独立芯片或简单串口连接。
3. 让原厂 CP 实际处理捕获的 `0x4063` 和 `0x4073`，从原厂生产路径取得 `0x2040`；独立核对 ACK、通知、长度、来源、时序和失败处理。
4. 在原厂 DMM/stream 生命周期闭合后提供明确的虚拟输入；验证原 CP 提交的 ISP 工作项及缓冲区消费。
5. 补足实际触及的 ISP 寄存器、DMA 和完成中断；缺少语义则停留未实现，不改为固定完成或软件滤镜。
6. 由原厂链路产生图像、编码、写入虚拟介质，再验收原厂回放和预览。QEMU 通过也不等同真实传感器、画质、回刷或恢复安全。
