## 静态契约：回复和通知是两件事

核对对象为固定客体提取的 `appFw.so`，SHA-256 为 `41bd8f4cda1f44c7038912837737e1ce6a650065f2108061ada30e5c7f9ce7c7`。下列均是该库的相对虚拟地址。

| 地址 | 可确认的行为 |
| --- | --- |
| `+0x3567490..74b4` | 命令 `0x4073`；根据调用参数分为关闭/开启 |
| `+0x35674f4..752c` | 开启时清零 `0x6d0=1744` 字节内部存储，并预先登记键 `0x2040` 的 future |
| `+0x3567550..757c` | 开启命令本身仍要求 12 字节回复；读取 `+8` 并与 `0xf000` 比较 |
| `+0x3567580..7584` | 命令完成后，再等待前述参数通知对应的 future |
| `+0x3555e5c..5e98` | 原厂收到 `0x2040` 后，把从消息起始处的 `0x6c8=1736` 字节复制到已登记存储的 `+8` |
| `+0x3555e9c..5ec8` | 兑现对应的原厂 future |
| `+0x35675e0..7894` | 解析多个参数区域、合法枚举和尺寸，再写入本次原厂模型对象 |

**1744 是含前置 8 字节成员的内部包装大小，接收器从通知起始处固定复制 1736 字节。** 这证明读取跨度，尚不能确定通知的允许总长度或尾部规则。先前把 1744 直接称为“开启命令的回复长度”不成立；这里以明确的寄存器参数和复制长度更正。通知首部、全部字段及生产时序仍须进一步核对，不能仅凭缓冲区尺寸宣布已掌握线协议。

当前没有发送伪造的长命令回复，没有填全零通知，没有直接写 AP ready 字段，也没有跳过原厂枚举/模型断言。

## 下一步的最小实现条件

1. 从原厂解析器建立 `0x2040` 字段表：消息偏移、宽度、转换函数、合法枚举、尺寸和相互约束；区分内部指针成员与线协议数据。
2. 完整保存并解析已出现的 `PID_SET_INIT` 2400 字节请求，判断哪些通知字段必须与先前配置一致。当前日志只留该请求的前 80 字节，不能拿它当完整参数证据。
3. 后续用户已明确要求追通原厂 CP／ISP，因此原先“由模拟器根据参数生成通知”的候选路线不再适用。必须由实际运行的原厂 CP 处理请求、产生 ACK 和 `0x2040`，再独立核对长度、来源、时序、所有权及发送失败。当前进展见 [原厂传输分析](native-cp-transport.md)。
4. 以原厂实际 `StartInOut`、插入事件和 Fsys 挂载结果核对槽位/文件设备映射。当前 `0x1010 → /nondev/rm2`、`0x1000 → /nondev/rm3` 只证明检测对象内部映射，不能等同实体 SLOT 或文件后端。
5. 得到原厂照片画面后再验证两张测试 JPEG 切换、返回与退出；当前无卡提示不满足这些判据。

这些是尚未完成的工作，现有证据不支持宣称照片回放或完整 CP 已实现。
