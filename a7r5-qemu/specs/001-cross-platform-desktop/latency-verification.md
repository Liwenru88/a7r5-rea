# Qt 按键与画面刷新优化

本轮仅修改模拟环境。没有连接相机、操作 SD 卡、读取或改写桌面原始分区镜像。性能数据来自本轮实际运行，不沿用上一轮文件时间推算。

## 测量与结果

先只加入分段计时，执行原有 Qt 验收，得到 `logs/latency-optimization/baseline-qt.json`。优化后用同一入口、同一组 16 次 QTest 鼠标点击复测，结果为 `optimized-qt-v3.json`。两轮按键顺序和每步像素 SHA-256 完全一致。计时包含工作队列、客体处理、快照传输与校验、Qt PNG 加载及控件更新；不测量物理屏幕扫描输出。

| 阶段 | 优化前中位数 | 优化后中位数 |
| --- | ---: | ---: |
| 点击到 Qt 更新完成 | 3368.65 ms | 442.21 ms |
| 按键、恢复及处理等待 | 1207.93 ms | 112.21 ms |
| 等待快照、导出及暂停 | 1849.49 ms | 257.03 ms |
| 单次解码校验 | 36.22 ms | 35.66 ms |
| PNG 路径，旧实现包含第二次校验 | 113.72 ms | 3.73 ms |
| 保存证据 | 0.56 ms | 0.49 ms |

点击延迟中位数减少 86.87%，约快 7.62 倍。16 次中的最大值由 3808.10 ms 降至 594.60 ms。各阶段分别取中位数，不能把表中数值直接相加当作端到端中位数。运行时负载会影响结果，不能将此范围承诺为所有 Mac 的固定延迟。

`comparison.json` 保存逐键数据、阶段统计和定义；两轮对应 `bridge/latency.jsonl` 保存 worker 细分，`run/latency.jsonl` 保存 QMP 恢复/暂停及串口命令耗时。`guest_ready_wait_ms` 是客体单调时钟读数，不能与宿主时钟当作同一计时源。

## 改动

1. 每键固定一秒等待改为新提交序列与像素来源稳定条件。20 ms 是短稳定窗口，2 秒为失败上限；超时不发布旧帧、不重试按键。重开 MENU 另等原厂 manager 返回菜单页面。
2. 完整容器用 RLE16 无损编码再传输。接收侧限制压缩及解压长度，拒绝零长度游程、截断、超长及多余数据，解压后执行原有 FNV、身份、几何、像素来源和 SHA 校验。原始 Base64 仍支持历史证据和独立验收。传输数据中位数为 67353 字节，原始容器为 639458 字节，二者都尚未计 Base64 膨胀。
3. 删除重复解码和 PNG 的 Base64 往返；以 Pillow 原生通道处理代替 Python 像素循环。所有 65536 种像素值的转换与独立逐值参考一致。
4. 串口读取排空已有数据后再等待；控制请求/回执轮询由 200/50 ms 缩短至 10/10 ms。保留独占请求、50 ms 成对点按及双方返回码检查、空闲 QMP 暂停。

## 验证证据

- Qt 实测：C4 帮助与 Enter 返回、四轮 MENU 开关、RIGHT/DOWN/ENTER/UP/LEFT/MENU。17 张真实原始容器逐一独立解码，与 PNG 像素逐值一致；保留历史独立预期值核对。5 秒空闲期间控制台不变，客体处于暂停状态。worker 和 QMP 正常退出。
- 定向回归：`test-frame-pipeline.py`、`test-frame-ready.py`，覆盖重复校验、全像素值转换、损坏容器、压缩边界、无新帧、损坏帧、原子替换、新序列等待回执及元数据连续提交。
- 相关会话、窗口、输入释放、指纹、沙箱、初始化与归档测试见 `logs/latency-optimization/regression.json` 及各模块日志。
- `integrity.json`：1226 个归档条目中仅 `simulation/headless-osd-export` 变化；QEMU、原厂内核、GPE 与其他归档条目一致。设备树仅相应更新归档结束地址与 ramdisk_size。没有修改原厂应用、观察库或原始分区镜像。

## 中间失败与限制

第一次候选因控制注册表仍绑定旧客体摘要，按钮被安全禁用，没有发出按键。第二次候选按整个容器序列做稳定判断，遇到持续元数据提交而超时，已正常退出 QEMU。测试程序原先在 pending 状态下未及时发现失败，本轮也已修正；该候选的 Qt 测试进程在确认 QEMU 退出后终止。上述候选均不作为成功证据。

当前只验收菜单交互。没有新增拍摄、录像、取景视频或未知实体按键，也没有移除沙箱、输入指纹、序列校验或空闲暂停。自包含应用包的交付与运行回执在本目录后续记录中单独列明。
