# 需求说明：跨平台客户端与相机控制面板

## 阅读摘要

目标是将现有网页控制入口升级为 PySide6 桌面客户端，继续显示原厂固件产生的真实菜单，并逐步扩展相机输入。首期交付 macOS Apple Silicon 上的客户端；Windows、Linux 的界面复用与模拟后端验收分别记录。

用户已授权本次实施 M1、M2（T001—T009）；M3 仍不实施。实际结果见 verification.md。

## 实施前基线（保留用于追溯）

- 项目：`<PROJECT>/a7r5-qemu`，Python 3.14.0、Apple Silicon macOS；PySide6、Nuitka、PyInstaller 均未安装。
- 网页入口调用 `tools/menu-ui.py`，子进程运行 `tools/probe-app.py`，通过文件控制通道和串口命令管理本次 QEMU。
- 当前正式控制白名单只有 `UP/DOWN/LEFT/RIGHT/ENTER/MENU`。`menu_live.py` 中删除、后拨轮的候选常量不等于 A7R5 验收通过。
- 既有记录：18 项检查、4 轮 MENU 开关、六键响应、15 张原始帧与 PNG 比对、QMP 正常退出。记录来自 `logs/`，本轮没有重新执行，不能作为新客户端的通过记录。
- `native_vm.py`、`vm_session.py` 仍依赖 macOS 沙箱、POSIX 锁、Unix 套接字和进程组；现有 Mach-O QEMU 不能直接用于 Windows/Linux。

### 包含

- 原生 Qt 控件、真实菜单帧、缩放、状态提示、相机控制面板与快捷键。
- 共用 Python 会话管理、结构化命令、平台能力接口、运行收据。
- 相机按键、摇杆、拨轮、选择器、快门两段及触控的完整盘点与状态呈现。

- 完整传感器、ISP、镜头对焦、真实取景视频、拍摄、录像与电源管理建模。
- 首期 Windows/Linux 的实际运行承诺、所有机型或所有 CPU 架构支持。
- 从源码重编 Sony 固件、云发布、自动更新、签名公证账号或证书配置。

## 需求与验收标准

### REQ-001：独立桌面窗口

用户可在客户端查看原厂菜单并控制模拟器。

- **AC-REQ-001-01**：启动客户端后出现独立 Qt 窗口，当前画面来自本次已校验原始快照；缩放保持比例。正常路径不打开浏览器、不启动 HTTP/WebView。
- **AC-REQ-001-02**：启动、按键处理和退出等待期间窗口持续响应；显示对应状态，禁止重复输入，失败不能继续展示为实时画面。

### REQ-002：会话、退出与错误恢复

每个窗口只控制其拥有的一次会话，退出结果可核对。

- **AC-REQ-002-01**：第二个会话不能绕过独占锁；启动中关闭、处理中关闭、初始化失败、进程意外退出或超时均保存证据，停止新输入，不自动重启虚拟器。
- **AC-REQ-002-02**：正常退出必须取得 QMP `quit` 和进程退出码 0；强制回收仅限本次拥有的进程，明确记录为异常回收。不得把“请求已接收”当作“已退出”。

### REQ-003：已有导航行为保持

客户端迁移不改变当前已验证的固件导航与空闲暂停行为。

- **AC-REQ-003-01**：六键在 Qt 按钮和快捷键入口均正确派发；原厂顶层 MENU 可关闭、重新打开至少四轮，导航序列画面与既有基线一致。
- **AC-REQ-003-02**：快照长度、身份、完整校验和、序列和 PNG 像素检查继续生效；输出后 QMP 暂停、输入前恢复，空闲期间虚拟时间不推进。

### REQ-004：完整控制清单与可信状态

用户能分辨已验证输入、候选映射和硬件限制。

- **AC-REQ-004-01**：按 A7R5 官方机身布局盘点可操作控制，覆盖按键、摇杆、拨轮、快门两段、模式选择器、电源和触控；每项记录标签、交互类型、映射证据、行为证据及限制。没有输入事件的纯机械控制也注明原因，不编造键码。
- **AC-REQ-004-02**：只有映射和指定使用场景响应均验证的动作可在常规界面启用；未知、候选、失败或依赖未建模硬件的动作禁用并说明原因。输入映射成功与对焦/拍摄/录像功能成功分别呈现。

### REQ-005：分批扩展输入语义

更多相机控制通过固件原有消息或状态接口实现。

- **AC-REQ-005-01**：每批新增控制先形成明确候选列表；按真实语义区分点按、按下/释放、长按、旋转增量、两段快门和状态选择，不能用普通键码统一替代。每个已启用动作保存 A7R5 的接收或分发证据、指定场景响应及正常退出证据。
- **AC-REQ-005-02**：界面失焦、用户取消或输入通道失败时不能留下未核对的按下状态；未知事件、越界参数、重复请求和超时不会被自动重发。发生固件异常时停止该项，保留日志，不穷举键码或无限试探。

### REQ-006：平台边界明确

客户端与可移植控制逻辑共用，平台代码按实际能力加载。

- **AC-REQ-006-01**：在缺少可用后端的平台，界面能明确显示“未支持/未验收”，禁止启动虚拟器；不因导入 `fcntl` 或 macOS 模块而提前崩溃，不回退到无隔离启动。
- **AC-REQ-006-02**：某平台只有在原生 QEMU 构建、隔离边界、输入完整性、根终端、真实菜单/按键和正常退出均实际通过后才标记支持。Qt 测试或模拟测试通过不等于该平台固件启动通过。

### REQ-007：隔离与输入完整性

继续保护原始资料与宿主环境。

- **AC-REQ-007-01**：默认拒绝隔离、固定输入摘要、路径范围和会话所有权校验继续生效；客户端只派发已声明的结构化动作，不提供任意 shell、任意队列或任意键码接口。
- **AC-REQ-007-02**：M1 的内核、客体归档和设备树保持现有摘要；M2 如确需修改模拟载荷，只能生成候选、验证除指定模拟文件外的条目未变，验收后切换。原厂应用、内核和库的适配改动须另行说明并确认；不读取原始镜像或设备。

### REQ-008：可启动交付与可回退

用户能双击启动，遇到问题可恢复已验证入口。

- **AC-REQ-008-01**：M1 在 Mac 上提供目录式 `.app` 交付；双击后不需终端激活环境，运行不依赖开发机 `.venv` 的绝对路径。Python/Qt 与固定运行资源按清单定位，固件归档只保留一份有效副本；可再生成构建缓存单列。
- **AC-REQ-008-02**：客户端和打包验收通过后才切换默认入口；网页作为显式回退入口保留，不自动切换后端。源码、依赖版本、运行输入与验收收据可对应；不删除原研究资料和历史证据。

## 澄清与边界

- 用户已选择跨平台技术方向，并确认本轮规划；没有授权本轮安装或实施。
- 采用上一轮提出的 Python/PySide6 方案；首期以现有 Mac 为实际验收环境。
- 当前项目 `AGENTS.md` 的“只用于 macOS”是现状边界。允许规划跨平台，但实施 Linux/Windows 前需明确授权并同步更新规则；M1 保持其设备与原件保护边界。
- Windows/Linux 验收主机及发行版版本尚未确定；不阻塞 M1 规划，M3 执行前必须落实。候选目标为 Linux x86_64、Windows x86_64，Mac 首期为 arm64。
- “所有按键”的交付首先是完整清单和状态，全部功能可用不是已有结论；无法证明的键不得为面板完整而启用。

## 风险与停止条件

- Qt 轮子、Python 3.14 和打包工具的兼容性需在实施首步核对；不自动替换现有 Python 环境。
- 长按、选择器可能触发未建模硬件路径；每项适配有独立停止条件，失败后不继续批量注入。
- Windows 的进程回收机制不等于文件/网络隔离；达不到隔离验收门槛时保留未支持状态。
- `.app` 可能涉及 Homebrew 动态库与冻结后子进程路径；源码模式成功不能替代包内运行验收。
