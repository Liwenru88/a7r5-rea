# SSH命令进入A7R5原始视图：方案与实施边界

## 目标与本轮结果

目标是让认证后的SSH命令、脚本和交互shell使用与libJit相同的原始挂载视图及root身份，同时保留既有认证、终端、SCP/SFTP和后台服务。本轮已核对本地启动器、libJit源码和既有实机记录，只生成此方案，没有连接相机、修改SSH配置或服务。

这里的“相同语义”优先指文件实际解析位置、UID/EUID、权限能力、工作目录和基础环境；标准SSH的交互输入、流式输出、会话寿命并不自动等于libJit一次性任务的15秒/32KiB限制。若要后者，需要另加固定任务监督入口，不能声称普通SSH天然具有这些门槛。

## 已确认的本地证据

1. `ssh-service/launcher.c:74-83` 在启动sshd前unshare挂载命名空间、将传播设为private，再覆盖整个 `/var`、只读绑定私有passwd副本，并挂载devpts。主机密钥复制到这个私有RAM视图的0600文件，账户修改不落到原始passwd。
2. `ssh-service/build.py:62` 使用 `Subsystem sftp internal-sftp`；当前交互方案移除了固定ForceCommand。内部SFTP不经常规外部shell包装器，因此只改shell/profile无法覆盖所有SSH文件操作。
3. `ssh-service/launcher.c:171-183` 的常驻父监督器持续执行parent_unchanged，检查账户、NSS、原厂sshd_config和关键挂载。若用户在原始视图有意改变这些文件，原逻辑会视为异常停止服务；迁移必须区分“认证实现不改原账户”和“用户root命令有意修改系统”，不能保留冲突却宣称语义一致。
4. `a7r5-libjit/src/runner.c:70-96` 的任务工作进程没有创建私有挂载命名空间，chdir到 `/`，以 `/bin/sh -c` 和固定PATH、LC_ALL、HOME执行脚本。02包的真实输出确认UID/GID均0、能力掩码 `0000003fffffffff`；`/`和 `/usr`只读，`/etc`、`/tmp`、`/var`均为 `/dev/nflasha10` 的VFAT视图。
5. 保存的旧SSH只读记录显示SSH与PID1/bootin具有不同mnt命名空间。它是历史记录，本轮未重新检查在线进程；命名空间数字和PID不能硬编码到新启动器。

## 推荐结构

```text
现有SSH认证入口（私有RAM账户、密钥和运行文件）
  └─ 认证后新建会话
       └─ 原始视图入口：核对目标身份 → setns(仅mount) → 核对root/cwd/能力
            ├─ /bin/sh -c 原始命令：脚本与非交互命令
            ├─ 保留既有PTY文件描述符的交互shell
            └─ 在原始视图运行的SFTP服务实现
```

登录认证继续使用私有账户，用户命令解析 `/var`、`/etc/passwd` 等路径时使用原始系统内容。认证后读取到原始root shell为 `/bin/false` 并不要求将原始账户改成可登录；会话入口直接启动经过批准的shell。但用户自己运行su等程序时，程序读取原始账户所产生的行为属于真实系统语义。

启动器在unshare之前记录并持有原始命名空间和根目录的可靠引用。会话入口核对持有者PID及启动时间、命名空间类型和inode、root目录及关键挂载，不能只相信PID1、固定数字、外部传入PID或用户可替换的路径。无匹配、持有者死亡、PID复用、能力不足或setns失败时，必须在执行用户命令前退出；不回退到私有视图假装成功。

仅加入目标mount命名空间，不笼统执行nsenter --all。root/cwd、身份、组和能力应单独比较；PATH、HOME、LC_ALL按libJit基础环境配置，TTY所需TERM及已建立的终端描述符明确保留。避免无条件source未知profile改变脚本行为，也不能把chdir或 `/proc/1/root` 路径别名当作完成命名空间迁移。

Linux文档说明，加入mount命名空间需要CAP_SYS_ADMIN和CAP_SYS_CHROOT等条件；目标4.9内核应使用 `/proc/<pid>/ns/mnt` 文件描述符方式，不使用5.8以后才有的pidfd多命名空间模式。API存在不代替当前机身能力检查：[setns(2)](https://man7.org/linux/man-pages/man2/setns.2.html)。

## SFTP与终端必须单独验收

普通命令、交互会话和子系统可以通过会话入口统一分派，但配置与OpenSSH 7.9p1实际行为须在目标环境验证。官方文档明确区分外部Subsystem与in-process internal-sftp；ForceCommand能接管shell、命令和子系统，并通过SSH_ORIGINAL_COMMAND传递原请求：[sshd_config](https://man.openbsd.org/sshd_config)。这些通用文档不构成厂商7.9p1二进制已兼容的证明。

新方案不能仅包装shell后让内部SFTP继续操作私有 `/var`。应先核实机内是否有独立sftp-server；若无，离线适配可在原始视图执行的外部SFTP服务，保留现有内部SFTP作为旧服务回退。在完整SFTP路径就绪前，不能切换整个现有服务或宣称现代默认SCP已迁移。

PTY已在认证侧分配后，进入原始视图可能改变 `/dev/pts` 路径可见性；须验证现有标准输入输出、控制终端、窗口大小、信号和正常exit，不在原始命名空间重新挂载devpts。

## 迁移与验证顺序

1. **离线阶段**：保留当前SSH和自启包，新建原始视图入口、命名空间身份记录和会话分派；补齐原始视图SFTP路径及父监督策略。检查当前原厂passwd、NSS、配置只被认证实现读取，不因新入口主动改写。原始系统被用户有意修改后的记录/停止策略必须明示，不自动恢复或覆盖用户更改。
2. **离线失败验证**：错误/过期目标、PID复用、命名空间或root不符、权限不足、setns失败均零用户命令执行；命令引号、空命令、stdin脚本、非零退出、PTY/信号/窗口、文件传输、连接中断和清理均有实际证据。执行入口不记录密码或私钥。
3. **QEMU**：仅在无物理设备透传的客体RAM中，用父视图/私有视图不同的哨兵文件，验证SSH命令与libJit读写同一个原始对象，私有覆盖仍只供认证使用；同时比较mnt/root/cwd/UID/GID/组/能力与只读挂载。测试绝不使用真实配置分区作为写入目标。
4. **实机预检与并行试运行另行确认**：先通过固定只读检查获得实际能力、命名空间、root和目标SFTP材料。用独立候选实例和独立端口验收，原2222服务保持回退；固定RAM哨兵读写及传输仅在明确批准的测试目录，不修改系统文件作为试验。
5. **切换另行确认**：正常终端、非交互命令、stdin脚本、SFTP/default SCP、正常exit及停止清理全部通过，再切换现有入口/自启材料。初次安装不重启、不替换旧库或覆盖旧服务；新实例失败只按本次监督和停止门槛结束，不重发启动或自动断电。

## 风险与确认范围

原始视图让命令作用于真实可写分区、IPC、进程和设备。root不会使只读的 `/`、`/usr` 自动可写；本方案不自动remount，也不证明原始分区镜像写回安全。新入口会扩大误写的实际影响，现有“父视图未变”回执也不能继续不加区分地适用于用户的任意写命令。

根据用户提供的AGENTS.md，权限安全行为变化和相机配置写入应先确认具体范围。建议下一次确认先限定为：**离线实现“私有认证＋原始会话视图”，保留原账户、现有SSH和自启回退，覆盖终端/命令/脚本及SFTP，完成失败验证和一次性安装包；暂不连接相机或安装。** 实机预检、候选安装和最终切换分别在具体材料可审阅后确认。
