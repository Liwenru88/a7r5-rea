# 子码109：密钥属性链路、诊断候选与最小补证方案

本轮结论：**实际失败已定位到持久安装目录中 `host_ecdsa` 的元数据门槛，但缺少当时的属性快照，尚不能确认四个条件中的哪一个失败。可以确定并修复的是109诊断丢失具体条件、并可能带出陈旧errno的问题。** 本轮没有访问相机、认证、DEBUG、启动SSH或修改相机文件。

## 1. 从生成到检查的证据链

目标会话：`2f94aea65af84dc6ab01a667752d283c`。`proof/child-result.bin` 实际回执：

```text
PRIVATE_RESULT code=109 errno=30 sshd_attempted=0 listener_observed=0 children_reaped=1 private_account_changed=1 local_banner_verified=0
```

`proof/stage.sh` 第5–7、19–33行的链路：

1. `umask 077`，创建 `/tmp/jiritsu/a7r5-ssh-service-<run>`，对目录执行chmod755。
2. 在该目录执行原厂 `ssh-keygen -q -t ecdsa -b 256 -N '' -f .../host_ecdsa`，随后对私钥及公钥执行chmod600。
3. `sync` 后执行同目录 `ssh-service.arm64 --launch`。脚本有 `set -eu`；结合本次确实取得该helper的父结果，可推断前面的生成和chmod没有向脚本报告非零退出。这不等于属性回读合规。
4. helper创建私有挂载视图，将私有tmpfs挂在 `/var`，在私有视图绑定只读账户副本并挂载devpts，然后检查**仍位于INSTALL_DIR的源私钥**。密钥并未复制到私有RAM目录。

原检查在 `proof/launcher.original.c:83`：

```c
lstat(INSTALL_DIR "/host_ecdsa", &st) ||
!S_ISREG(st.st_mode) || st.st_uid || (st.st_mode & 077)
```

这四项分别是：路径元数据调用失败、非普通文件、所有者非root、组或其他用户有权限。它不是“必须恰好0600”的比较，也不检查gid。候选保持这些语义，不新增或删除权限条件。只有之后才创建私有sshd配置、日志并执行 `sshd -t`，因此109时尚未启动sshd，诊断文件不可读取与该阶段相符。

## 2. errno与文件系统：哪些能确认

原第79行特意以写方式打开私有只读账户，要求失败errno为30。若之后的lstat成功，而某个纯属性比较失败，旧finish逻辑仍可能把30写进109结果。

本轮最小复现用“普通文件、uid0、0644”触发权限拒绝，旧逻辑确实输出 `code=109 errno=30`。这证明诊断存在误导路径，**不证明实际相机上的私钥就是0644**，也不证明lstat失败或密钥所在文件系统只读。

保存的固件fstab含Sony扩展 `posix_attr`。它能说明部分VFAT挂载使用扩展属性，不能据此确定当时 `/tmp/jiritsu` 的有效挂载选项，更不能套用普通桌面FAT行为认定chmod无效。此前QEMU验收脚本只是 `mkdir -p /tmp/jiritsu`，没有按实机工作区的VFAT属性语义构建该目录；因此模拟中chmod成功不覆盖这个实机风险。

原厂 `create_host_key.sh` 将密钥生成到 `/tmp_network/ssh`；已保存的a7c2参考脚本也用 `/tmp_network/a7c2ssh`。当前A7R5常驻候选改为把密钥放在持久INSTALL_DIR，目的是维持主机身份，但引入了需要验证的源文件属性。参考方案并不能证明把密钥直接迁到RAM就满足当前持久身份需求。

ABI核对：沿用的AArch64 stat声明为128字节，本轮目标编译通过，且与旧包头文件逐字节一致；未发现这次改动引入的布局差异。本轮未执行AArch64客体，不把本机C测试或编译称为目标ABI实机验证。

## 3. 已准备的最小候选

### 诊断修复候选：保持拒绝门槛

`launcher-key109-detail.patch` 与 `src/key109_metadata.h`：

- 每次lstat前清空errno，立即保存返回值及本次errno；成功时报告errno0。
- 保存mode、uid、gid、size与有效性。失败时字段标为无效，不把清零缓冲区当作真实属性。
- 拒绝位：1=查询失败，2=非普通文件，4=非root所有者，8=组/其他权限；允许同时显示多个原因。
- 原有检查仍拒绝相同输入。纯属性拒绝时子109的errno置0，避免沿用30。
- 在本次私有RAM中写 `key109-metadata` 后才继续；诊断格式化/落盘失败用新增125中止。未来主机策略必须显式处理125，现有已封包入口不会自动接受它。

这份补丁只在本机独立副本生成并编译成对象，**没有合入生产launcher、旧包或安装相机**；合成配置不含用户密码。它修复的是诊断，不是已经确认修好了相机密钥。

### 推荐补证：4,736字节固定元数据探针

`build/key109-metadata.arm64` 固定查询原INSTALL_DIR和其中的 `host_ecdsa`，不接受路径参数。程序只做root身份检查、两次lstat及stdout输出：没有open/read私钥、chmod、chown、生成密钥、账户修改、进程派生或SSH代码。

它可以区分当前路径查询错误和各属性拒绝位；**查询的是执行时的当前源文件视图，不能还原旧109发生时的快照，也不复现完整私有命名空间。** 父目录单独输出且标明不套用私钥门槛。采集完成返回0只表示取得报告，不表示密钥合规或SSH可启动。

## 4. 实机最小方案与风险（尚未执行）

现有已验证服务文件读取入口不返回stat字段，RAM里也没有旧属性报告。本轮没有另找或试发未知协议。若要取得元数据，需要另行封装固定探针的一次性执行入口；当前材料包不是可双击实机安装包，不含实机批准。

建议下一步先封装再提交确认：

1. 绑定原密钥路径、当前已验证普通USB端口及新执行nonce，先核对版本、固定旧会话结果和精确512换行预加载。
2. 上传约4.7KB探针和专用一次性执行库；固定脚本只校验探针摘要并执行，不创建/修改源私钥、账户或SSH配置。
3. 这会需要新的固定文件及预加载写入、两阶段认证/START、一次DEBUG；与刚完成的纯文件读取会话不同。执行库触发后先中和预加载，输出带新执行nonce的状态/报告，保留固定文件残留。
4. 两条完整元数据记录、明确结束标记、执行器终态及前后512换行全部通过才考虑一次STOP；诊断中的拒绝位或明确lstat错误可作为采集结果，不触发自动权限修复。协议错误、探针未结束或未知预加载一律停止，不重试、不重建旧现场。
5. STOP仅一次，随后核对普通USB、媒体及屏幕；不自动断电。新增诊断执行同样有USB停留服务态、载荷/输出残留及恢复受限风险，须在具体一次性包准备完成后另行确认。

读到数据后的分支：查询失败先按原始错误和目录记录定位；非普通文件或异常所有者不自动覆盖；若确为权限不符，再评估固定路径修正并回读，或在核对持久密钥来源及身份后于私有RAM建立0600副本。只有RAM执行副本合规而源文件来源/稳定身份也得到验证，才讨论再次启动SSH。当前不把改放RAM、关闭检查或重生成密钥当成已验证修复。
