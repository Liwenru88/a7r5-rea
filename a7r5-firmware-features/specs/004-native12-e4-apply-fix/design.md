# 调查与修复设计

生产选择链为CP SELECT确认→原E4构造并排队→原E4九次参数分派返回→第二次SELECT确认→持久化选择文件→生产所选及UI成功。必须保留该门禁。已有QEMU服务只覆盖加载协议，未覆盖原E4全部依赖；目前不能据此断定是固件错误。

首先在`a7r5-qemu/experiments/native12-410-menu/`的独立构建中加入只观察的原生执行追踪。原厂E4入口`AP+0x348292c`及其九个分派入口可用严格前像校验的RAM跳板保留原指令执行；观察OSAL请求，不修改其结果。先复现原失败再实现服务。原始输出留在新`build/`和`runs/`，不覆盖历史。

修复优先落在该实验的模拟服务和构建器；底层消息必须依据原厂请求／接收器布局实现窄范围服务，不接受未知请求，更不能无条件返回成功或直接调用私有完成包装器。CP私有协议仍在独立ARM QEMU中执行原CP代码；必要的原生参数消费也应保留真实执行证据。新增模拟边界必须写入构建回执。

最初AP／CP等于4.11包内组件；后续已确认私有菜单值刷新重入，需要独立AP覆盖层。清单明确区分4.11来源与未封包的派生AP；不能把来源DAT摘要解释为新AP已在该包内。固定上游、默认runtime、历史4.10／4.11均保持。

定向复现/失败保护为V1/V2；最终真实Qt全链路及生命周期为V3。验收从多个独立证据交叉核对：生产AP状态、原E4对象执行返回、CP状态/回执及客体持久化文件；截图只证明界面，不单独证明应用成功。归档与中文分析写在本spec的verification.md及模块verification目录。

## 实际阻断与隔离验证

原厂E4进入公共队列0。最先阻断它的是C3触控配置（BB `0x146`），并非滤镜参数非法。补齐严格虚拟触控协议后，已观察原E4九次分派及原体返回。公共队列随后继续等待成像释放锁、HDMI／显示配置、Dataflow端口和辅助配置；这些服务不能用E4替身替代。

显示依赖推进后，原UPM在`FULL→SLOW`转换中关闭中断并轮询`0xf1388f50`，而通用外设占位值不能满足条件。独立客体使用原厂OSAL接口`0x80920901`的`LOCK_MODE(6), DEBUG(10)`持有频率锁，原UPM实际回报`DFS_STATE_FULL`、`DFS_FREQ_AVB_FULL_CPU_FULL`及DEBUG锁；未修改内核模块或伪造DFS完成位。锁仅贯穿本次VM生命周期。

继续启动将要求`PID_SET_NOTIFY_MODE ON(0x4073)`之后的`0x2040`成像状态通知。原消费者复制1736字节进入1744字节内部对象；当前未实现该状态模型，不能随意填零或伪造成像就绪。完整拍摄初始化仍未通过。

新增显式`--menu-isolation`，只通过两个原厂MENU输入进入菜单，在确认触控引导和启动拍摄初始化之前验证滤镜控制链。没有写首次设置字段或跳过E4。这是有限的组件隔离证据，审计状态必须为`PASS_MENU_ISOLATION`，不能替代完整启动和四轮MENU往返。

只读观察器的共享快照以零标记表示写入中；QMP若恰好暂停在该窗口，允许短暂继续客体后最多重采样20次，保留每次原始样本。未知标记、截断及持续未完成均拒绝，不补写生产状态。原有E4五秒和CP一秒门禁均保持。

## 已确认的固件菜单缺陷

只读原dispatcher事件追踪确认：`0x2010003`导航失败后，私有页和命令状态均为3；后续`0x20f0001`值刷新事件进入原厂D9处理器，命令状态从3变为1，未经新按键再次提交目标。成功场景也会产生额外逻辑请求，只是原有重复选择快速路径阻止了CP/E4额外事务。该重入会破坏错误终态，属于独立于硬件服务缺口的实际固件问题。

新增`native12-combined/e4-menu-compat.c`及`e4_menu_compat.py`，对精确字体修订AP施加104字节覆盖层：原私有dispatch入口4字节跳转至新代码；只有控制器、管理器、PAGE=0xD9的所有权均匹配时消费`0x20f0001`，包括尚未销毁的退休私有对象。其余事件／页面执行原入口前16字节后继续完整原体。没有写可用位、状态、选择或刷新完成字段，不修改E4执行器／上游快照。

仅改变104字节原RX零填充窗、4字节原入口及现有PHDR的16字节长度字段，仍在同一RX映射页，精确逆还原通过。派生AP SHA256为`65e33ba2075bb59f65a97e6cec550bd8b1d54bac040fe28427cd3922924ffde0`，未封入冻结4.11 DAT。QEMU新运行和固件CPU回放均按该摘要验证。
