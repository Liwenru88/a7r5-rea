# 4.19 封包、WBI 与更新后启动离线审计

审计日期：2026-11-11。范围为现存全功能 4.19 更新包、当前构建器及最新未封包组件；不连接相机，不修改运行时、更新器或已发布升级包。

## 结论

**未发现现存全功能 4.19 包存在“WBI 先清理、随后又恢复旧有效头”的缺口，也未发现已检查范围内的分区越界、CP 页表后移或 ELF 加载段重叠。但不能据此保证机身升级后一定启动。**

本次确认两个不同层面的缺口：

1. **当前包继承了原厂 NOR 写入错误漏报。** 如果设备进入 NOR 更新分支，擦除或写入失败后仍可能向上返回成功。这是“更新看似完成，首次启动失败”的直接条件性路径；本次用替身命令重新复现，尚无实际设备发生该故障的证据。
2. **独立模块的 WBI 策略不统一。** 当前全功能包、24 槽、画幅和 AF 单选会清零 WBI 首扇区；FL2／FL3、C1–C6、旧版电子快门声、NTSC、构图标记的单选计划保留原厂 WBI。它们修改 AP／CP，却会重新写入带 `WBI2` 头的原厂快照。这是可确认的打包策略缺口，可能恢复旧代码或造成新旧状态混用；离线证据不能推导为必然变砖，也不影响本次已清零的全功能包。

建议优先补齐这两项保护。不要把 WBI2 清理当作所有启动故障的唯一修复。

## WBI：当前全功能包已形成包内闭环

`nflasha5` 是分区表中的 Warm Boot Image 分区，容量 314572800 字节。`WBI2`／`WBI3` 是镜像头标记，本次证据没有显示两个分别叫 WBI2、WBI3 的独立分区。包内载荷为 243789184 字节，不能把载荷长度误当作整分区长度。

本次核实最终包中的 WBI：

- 偏移 `0x000–0x1ff` 为 512 字节零。
- 首扇区后的每个字节与原厂 4.00 镜像相同，长度不变。
- SHA-256 为 `9f20893ec28a1780701bb42a6eaad3e2574623c62ba4d733d19e12ef0479650b`。
- CRC32 为 `dfa823fc`，与包内 `part_image.sum` 指定的长度和 CRC 一致。
- 分区表、更新器及相关执行顺序保持原厂；没有通过改变分区地址实现清理。

从当前包的 `updater.bin` 解出相关程序，逐字节确认与之前逆向的原厂程序一致。结合原厂调度反汇编和同步配置，执行次序如下，序号从 1 开始：

```text
27  partconf.sum → us_mkfs.sh → ud_wbi_drop.elf：清零设备首扇区
92  nflasha5：把本包已清零首扇区的镜像写入设备
96  part_image.sum：按指定长度读设备并计算分区 CRC
100 nor_loader.sum → nor_loader_writer.sh：按机型启动配置处理 NOR
    endupdate.sh → 更新完成 → 重启入口
```

当前结束脚本未发现再次写回 WBI 有效头的动作。因此正常写入路径的结果是 `WBI2 → 0 → 0`，与旧包 `WBI2 → 0 → WBI3` 不同。

本次用当前包确认一致的原厂指令回放了清理、镜像写入和首扇区 CRC 消费：清理成功后仍为零；即使初次清理零字节短写被原厂程序错误当作成功，后续本包镜像写入也会覆盖旧头；旧头残留导致 CRC 不同，CRC 读取短读被拒绝。回放使用模拟 I/O，未执行完整更新或前置引导器。

这说明包内失效状态和后续校验一致，**不等价于已验证实际介质落盘、掉电行为或机身冷启动分支**。也没有证据支持为此擦除整个 300 MiB 分区；目前采用的是与原厂清理动作一致的首扇区失效。

实现依据：[core/native24.py:186](../../core/native24.py#L186)、[prepare_wbi](../../native24-combined/release417/container_package.py#L157)。原厂执行顺序的逆向依据见 [4.18 启动分析](../../native24-combined/4.18启动故障离线分析.md#WBI-清理顺序复核)。

## 直接缺口一：NOR 擦写失败可能被当作成功

当前 `updater.bin` SHA-256 为 `c4b18a82eea52a507fb82b86ad50bab6047070b8908d03c28edcce4a9577d348`，与原厂相同，其中 `nor_loader_writer.sh` 也逐字节相同。

两个函数的行为有明确问题：

- `write_flash()` 调用写入命令后执行 `echo`，函数返回的是最后一次 `echo` 的状态。
- `erase_write_flash()` 不检查擦除结果，继续写入，也不检查写入结果，最后执行 `echo`。
- `nor_update()` 调用 CP 擦写后继续记录日志并显式 `return 0`；外层虽然检查它的返回值，但无法看到已经被吞掉的错误。

只提取这两个函数，将实际写入命令替换为本进程内的无设备函数，重新执行得到：

| 擦除返回码 | 写入返回码 | `erase_write_flash()` 返回码 | 独立 `write_flash()` 返回码 |
| --- | --- | --- | --- |
| 7 | 0 | 0 | 0 |
| 0 | 7 | 0 | 0 |
| 7 | 7 | 0 | 0 |

分区 CRC 在序号 96；NOR 处理在序号 100。因此 **eMMC 中的 `cpapp-b.bin` 通过 CRC，不能证明物理 NOR 中的 CP 擦写也成功**。在失败后其余步骤成功的条件下，主流程可能继续报告完成，重启后才暴露不完整或新旧不一致的 CP。

此路径仅在硬件配置进入相应 NOR 分支且底层操作失败时触发。不能据此声称每次更新都会失败，或重新认定历史 4.18 变砖的唯一原因。

源码依据：[原厂写入函数](../../../a7r5-fastboot/private/cases/4.18-incident/wbi-order/updater/bin/nor_loader_writer.sh#L145)、[CP 写入及强制成功](../../../a7r5-fastboot/private/cases/4.18-incident/wbi-order/updater/bin/nor_loader_writer.sh#L271)、[分支条件](../../../a7r5-fastboot/private/cases/4.18-incident/wbi-order/updater/bin/nor_loader_writer.sh#L294)。故障注入输出在 `evidence/audit.json` 的 `nor_failure_injection`。

### 最小修复方向

先逐次检查擦除、写入和传输模式设置的状态；失败立即沿调用链返回，禁止继续覆盖后续区段、禁止报更新完成。同步补查本脚本中生成镜像、挂载、复制、卸载的关键返回值，避免输入文件不完整时仍开始擦写。读回比对应先确认原厂工具支持的接口，不能臆造硬件读回命令。

这是更新器硬化，不能只改普通功能补丁。当前 `core/package.py` 明确要求更新器摘要保持原厂；实施时必须设计精确前像、允许修改集合、SquashFS 容量与容器布局检查，并执行失败注入和独立解包验证，不能简单取消摘要门禁。**本次只分析，未修改更新器或生成包。**

## 直接缺口二：单选构建仍可能重新激活原厂快照

本次实际调用当前 `make_plan()`，得到：

| 配置 | WBI 策略 |
| --- | --- |
| 当前十模块全功能、24 槽单选、十档画幅单选、AF 单选 | 首扇区失效 |
| FL2／FL3 单选、C1–C6 单选 | 保留原厂 WBI2 |
| 旧电子快门声音单选、NTSC 单选、构图标记单选 | 保留原厂 WBI2 |

这里的“声音单选”是模块默认的旧电子快门补丁；机械／电子双组声音变体目前只允许全功能组合，不受上述单选策略影响。

原因是规划器只在 `native24 or capture` 时把 WBI 放入变化集合；色彩构建的 `native24.apply()` 在没有 native24／capture 时提前返回，通用字节补丁路径也没有公共 WBI 失效步骤。现有测试还明确断言部分单选不修改 WBI。这是已存在的设计，而非本轮文件损坏。

原厂更新流程会先清理首扇区，但后面仍会写入归档中的完整原厂 WBI2 载荷。修改了 AP／CP 却保留该快照，缺少“必须重新从新组件初始化”的统一约束。可确认的是最终镜像和策略不一致；恢复旧代码、功能未生效或新旧状态混用是需要引导器／设备证据确认的后果，不能把它们写成已复现的变砖结果。

最小修复应将 WBI 失效放到公共封包步骤，由最终 AP／CP／AVCAM 等启动相关组件是否改变决定，而非依赖选中了哪个模块。需要同步修改计划变化集合和最终回读断言；不能只修改 `plan.py` 一个条件，否则实际变化集合校验会拒绝构建。仅修改 R6／AWB 模板时不应不加区分地归入代码镜像变化。

依据：[规划条件](../../core/plan.py#L185)、[色彩路径提前返回](../../core/native24.py#L186)、[通用构建分流](../../core/package.py#L124)、[历史测试约束](../../tests/test_compose_phase3.py#L17)。

CP 的页表地址在实际启动指令中计算并写入，文件中 `0x108f1c` 对应的初始零值不能当作页表地址异常。本次只读探针的一个中间版本曾误用描述符的装载地址计算运行区末尾，已改为运行地址；失败中间目录保留，不作为通过证据。

目前没有完整 NOR 加载、CP 就绪、AVCAM 初始化和 AP 初始化串联成功的离线证明；没有相机启动日志。尤其 CP 在 MMU 开启前进入扩展地址的实际可用时序，局部指令回放只能证明镜像完整装入时的行为。不要据此标记整个启动链已验收。

```sh

A7R5_FINAL_READBACK="$PWD/.local/full419-readback-v2" \

  a7r5-firmware-features/tests/test_full419_integration.py::test_actual_sound_page_keeps_original_root_and_rejects_corrupted_code_and_pte
```
