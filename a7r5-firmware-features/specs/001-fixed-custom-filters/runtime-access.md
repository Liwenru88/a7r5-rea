## 实现范围

在已锁定修改4.06的原通信任务中研究一次性启动，新增运行时不创建额外线程或future。C实现位于[af_runtime.h](../../custom-filters/native/af_runtime.h)、[af_runtime.c](../../custom-filters/native/af_runtime.c)和[AP系统适配](../../custom-filters/native/af_runtime_ap406.c)，指令联验位于[native_runtime.py](../../custom-filters/a7filters/native_runtime.py)。旧HELLO接收入口与新启动挂钩共同构建，只有`AF_RUNTIME406`启用时才连接新运行时。

| 原位置 | 已核对前像/服务 | 接入行为 |
|---|---|---|
| AP注册`0x3552d50` | 原`0x3702c20 → 0x3702ae4 → osal_create_waitable_thread` | 登记`IWrapperImaging`，入口`0x3554cf8`，身份64、优先级8；线程创建边界只记录参数，不创建宿主线程 |
| AP接收`0x3554d38` | `36188697`，原BL `osal_rcv_msg_tmo` | B到新跳板，首次进入创建会话并发送HELLO；有消息回`0x3554d3c`，空接收回`0x3554d24`，不解引用空指针 |
| CP任务`0x495fd8` | `f0b503af2de9000f` | 首次任务启动只初始化状态0，重放原序言后回`0x495fe0`；状态4/5等均不重置 |
| AP/CP种类解析 | `0x3554d90` / `0x496044` | 沿用第十六批私有HELLO分流；CP回复和AP归还仍走原发送器/消息池 |

四个分支只改匿名模拟内存，前像、分支范围/Thumb入口严格核对，结束后恢复原字节及模拟器翻译缓存。AP新接收跳板使用同一完整保存宏，保护通用寄存器、Q0～Q31、NZCV、FPCR/FPSR。真实装载位置、线程栈、指令缓存维护、异常和完整线程初始化仍未验证。

原AP注册器的执行还核对原登记对象`0x8e82e98`和句柄落点`0x89bcd80`；线程创建返回值为显式夹具。线程内部`0x3695b30`的TLS/任务登记没有被伪造为已执行，不能称为完整AP启动。

## 会话与时钟来源

| 来源 | 原AP导入 | 实现约束 |
|---|---|---|
| 随机会话 | `open 0x16d9740`、`read 0x16d9840`、`close 0x16dba00`、`__errno_location 0x16db580` | 原包`0x35bb54c`已有`/dev/urandom`读取通路；新代码读取8字节非零值，处理短读/EINTR，总计最多16次读取；打开、EOF、关闭失败或零值均拒绝，不退回固定值 |
| 单调时钟 | `dlsym 0x16dac90`解析`clock_gettime` | 指定`CLOCK_MONOTONIC=1`，检查返回值、非负秒、纳秒范围及毫秒转换溢出；同包libstdc++的`steady_clock::now 0xb1208`也实际传1给其原clock_gettime PLT `0x891e0` |
| 退避 | `usleep 0x16daf60` | 空接收伴随异常结果时请求50000微秒退避，私有协议保持故障，不重发或自动重建 |

PLT地址由同一锁定AP/C++库的ELF重定位符号再次核对，不根据其他固件版本猜测。所有上述系统服务均在目标导入边界使用显式内存后端；分析进程不打开宿主`/dev/urandom`，不调用目标系统时钟、物理IPC或宿主线程服务。

会话是64位随机标识，提供概率防碰撞，不是严格永久唯一，也不是认证。它还不能直接满足未来整预设/银行重建对唯一代号和安全排空的全部要求。CP仍绑定首次会话，AP单独重启通常会被旧CP拒绝；不为恢复而清除CP在用银行或帧。真正重建须补齐双端启动代号/排空及持久代号策略，不把新随机值等同于安全恢复。

## 循环、截止与故障

运行时使用独立的40字节状态：`AfHandshake`、最近毫秒值、是否已尝试启动和首个故障原因。一次启动最多发送一条HELLO；故障、过期和后续原消息都不会重新读取随机源或自动重发。

等待HELLO时，原OSAL每次接收至多等待50毫秒，临近截止时缩短到剩余毫秒。调用前后及私有回复处理前读取单调时钟，因此持续收到其他消息也不会阻止过期。截止总长1000毫秒，等于截止即拒绝；时钟回退或服务错误使状态进入故障。握手结束后恢复原无限接收参数−1，仍可处理原厂消息；这不是持续链路健康探测或断线恢复。

原OSAL路径`0x6468 → u_osal_rcv_msg_tmo 0x3c60`实际执行，目标ioctl为`0x80000007`。有消息交回原分派；无消息只在有界等待且结果为原空队列/超时值−1022时作为正常轮询。其他空错误关闭私有协议并请求退避。驱动真正的等待时长/调度及信号打断仍未执行，不以隔离后端推进时间冒充物理超时验收。

HELLO发送调用原分配器，wait=0，完整复制128字节、原函数写来源后调用原发送。分配或发送失败立即关闭私有协议。**AP驱动发送失败后的缓冲所有权尚未查明**，没有猜测free，也没有声称失败路径消息缓冲已回收；这是安装门槛。原消息的非空输出继续交回原路径拥有，不因私有故障直接丢弃。

## 缓冲占用与版本关联的新证据

[cp_notifications.py](../../custom-filters/a7filters/cp_notifications.py)继续执行原占用函数`0xb2b37e`、归还`0xb2b42c`及标志函数`0xb2a5a4`：

1. 句柄7首次占用成功，重复占用返回−10；占用登记为`0x378`、头为`0x20`。
2. 归还后再次占用同一句柄，得到相同登记和头，没有观察到代号变化。
3. 用夹具重放旧拥有者的同句柄归还，原代码会清除当前登记并重新标记`0x80000020`。这是原接口缺少版本辨识的反例；没有声称真实迟到回调已经发生。
4. 归还句柄7使全局`0x1934564=1`，占用另一个句柄8又将它清0，但句柄7的归还头仍保留。该全局量不是“所有帧已结束”的汇总屏障。

互斥0x35、线程上下文和诊断使用显式后端；实际占用/拒绝/归还/标志更新执行原指令。像素分配器重用、DMA完成、所有借用者及最后图像帧依旧未证明，不能安装`af_apply_owner_end`。需要把完整会话/版本/租约关联到真实资源拥有者及每个借用者，不能直接拿句柄、低16位通知或全局标志代替。

## 验证与剩余工作

最终目标入口15组联验、177项回归、ASan/UBSan 20000次探测、构建命令和复算入口统一记录于[第十七批交付](continuation-17.md)。完整同包审计151.514秒通过，执行期间源码保持。终检另复现并修正了时钟回调缺失时沿用旧时间值的边界，修正后重新执行全部上述验证。

当前只增加原任务接线和生命周期证据，不发布纯参数银行、不创建滤镜应用成功回执。T03f/T07仍须补齐真实照片EVF/JPG消费者和完整银行集合、最后图像帧；T08b仍缺ISP格式/域/基底模型和量化测量，不能生成有意义的拟合色表或误差保证；T05/T09仍缺合法机内路径、实际菜单及真实应用回执。它们继续需要离线逆向和实现，不能归为只差实机验收。
