# 第十六批：原消息入口与私有HELLO双向接入

- Feature ID: `001-fixed-custom-filters`
- Updated: `2026-10-26`
- Status: `OFFLINE_NATIVE_HELLO_VERIFIED_NOT_INSTALLABLE`

本文保留第十六批范围。第十七批已补齐原通信任务一次启动、系统导入的随机会话/单调时钟及原接收循环轮询的限定离线接入，详见[运行时接入](runtime-access.md)；完整线程/系统服务和成像仍未验收。

## 当前结论

新增AArch64/ARMv7入口已在同一修改4.06的匿名AP/CP内存中安装实际分支，私有HELLO经原AP发送窗口、原CP发送器、原AP接收窗口和两端原消息释放执行完成。成功进入兼容确认，延迟、损坏请求、CP回复发送失败均不确认；默认关闭、旧消息委派及私有PRESET不写入成像状态也已验证。

这是入口级离线接入；虚拟队列搬运和时钟仍是明确后端。没有真实机身握手、启动初始化、UI事件或事件循环接线；没有把HELLO确认变成照片参数已应用，整套功能仍未完成。

## 已实现的入口

| 位置 | 改动及返回 |
|---|---|
| AP `0x3554d90` | 原来源检查后、种类解析前，4字节B到`af_ap_hs_gate`；私有包转原`0x3554ec8`释放，其他包重放原`ldrb w0,[x19]`并返回`0x3554d94` |
| CP `0x496044` | 原任务获取`0x24`之前，8字节绝对Thumb跳转；私有包转原`0x49606e`消息释放；其他包重放原互斥获取和首字节读取，再回`0x49604c` |
| CP回复 `0x496180` | 新CP入口调用已核对原发送器，长度128、目的`0x80020002`；来源由原`0xbaaaa0`写为`0x90030001` |
| AP发送 `0x35589a4…0x35589dc` | 执行原分配/复制/发送窗口及同包OSAL库，128字节、目的`0x90030001`、来源`0x80020002` |

代码：[通用握手](../../custom-filters/native/af_handshake.h)、[核心](../../custom-filters/native/af_handshake.c)、[AP桥接](../../custom-filters/native/af_hs_ap406.c)、[AP汇编](../../custom-filters/native/af_hs_ap406.S)、[CP桥接](../../custom-filters/native/af_hs_cp406.c)、[CP汇编](../../custom-filters/native/af_hs_cp406.S)。接入执行器为[native_handshake.py](../../custom-filters/a7filters/native_handshake.py)。

两处前像分别严格核对`60024039`与`242022f192ee3078`，AP分支检查有符号范围和对齐，CP目标使用Thumb入口。结束后精确恢复原字节，并撤销模拟器翻译缓存。全部改动仅位于匿名内存；输入AP/CP、DAT和既有研究ELF均未改。

AP跳板保存X0～X18、LR、NZCV、完整Q0～Q31及FPCR/FPSR；C ABI负责其余通用寄存器，跳板占704字节栈。独立哨兵测试实际复现旧跳板的SIMD破坏，再补齐保存恢复。真实线程栈预算、异常展开、装载权限和指令缓存维护仍须单列验证，不能用模拟器缓存操作替代。

## 私有包与握手状态

沿用第十五批固定128字节`A7P1`格式，不分配Sony命令ID。两端只在已核对来源、原分配器声明长度128且完整魔数匹配时接管；其余消息继续原逻辑。包内仍检查协议版本、父AP/CP构建SHA、会话、必要消费者掩码、保留字段和CRC。CRC只检测损坏，父SHA不是运行映像测量或认证。

握手仅使用HELLO操作。CP对首个合法会话固定绑定；同会话可幂等回复，其他会话不回复，直到可信调用者显式重建。AP确认需要当前会话、版本/父构建/掩码一致、合法CRC，以及在截止时间之前到达。超时等于截止时间即拒绝；过期状态不因迟到回复或时钟回退而恢复。

| 状态 | 含义 |
|---|---|
| 0 | 未配置；默认不启用私有入口 |
| 1 | AP等待HELLO回复 |
| 2 | 协议兼容性已确认；不表示银行或照片已生效 |
| 3 | 已过期，迟到回复不确认 |
| 4/5 | CP已配置但未绑定/已绑定首个会话 |

`af_ap_hs_begin`必须显式传入非零会话、必要消费者集合、超时及单调时钟函数，成功后才启用AP入口。`af_ap_hs_poll`即使没有回复也可使等待到期；真实事件循环尚未调用它。研究测试的会话43、时钟100/150是明确夹具，不代表已经找到了机身启动会话或时钟提供器。CP重建前必须在后续实际集成中证明连接、银行及帧已排空，目前未接入自动重建或断线恢复。

有效PRESET包也会被当前仅HELLO的服务消费并拒绝，不写`0x157aa10`、不发布银行、不产生应用成功回复。原32槽AP界面仍没有调用新握手或成像协议；不能因为状态2就开放实际应用。

## 原AP完整包装器与等待边界

[ap_request.py](../../custom-filters/a7filters/ap_request.py)从真实基底发送器`0x35614b4`进入原完整包装器`0x355882c`，执行原future/共享状态构造、引用和析构，使用同包C++库和OSAL。成功消息再进入原CP完整消息任务、快照及颜色/锐度派生；不是只直接调用发送子窗口。

- 正常单向发送及注入−7失败，两种情况都释放48/32字节的两个C++对象，保护区保持。
- 发送失败后原发送器仍将输出状态写0，不能把它解释为版本已应用。传输缓冲在失败时由驱动还是调用方拥有仍需确认，C++对象已释放不能替代这一合约。
- 原带回复请求注册第三个48字节节点后，进入libstdc++的futex调用边界：系统调用号98、等待操作0、期望值`0x80000000`、超时指针0。在执行宿主syscall前停止，不伪造回复或唤醒；这不是“请求完成”，也不能作为新握手的有界等待方案。

源库在明确研究基址按需映射，最多64个源页；只绑定已知ELF重定位和同包符号。分配/释放、诊断、锁和系统接口是显式后端。库线程存在弱标记为0，验证的是该库的串行分支；没有执行真实库初始化或AP整体启动。

## 原CP消息生命周期

[cp_message_pool.py](../../custom-filters/a7filters/cp_message_pool.py)执行`0x53c220 → 0x53c660 → 0x53d394`原分配、原任务`0x496018…0x496076`和`0x53c31c → 0xbaaaec → 0x53d544`原归还/合并。消息头24字节：来源在载荷−12，长度在−8，16位引用数在−14。消息长度上限在原分配器中检查为4096。

默认消息分派后引用1→0并合并回4KiB空闲块；显式夹具引用2时，原任务只减到1，额外拥有者结束后才归还。原不支持命令`0x4004`会生成原格式`0xf001`错误回复；发送失败走原消息释放，而不是在Python中直接清空计数。

未安装私有入口的原CP面对合法128字节HELLO，会忽略未知首字节并正常归还，不会回复HELLO。由此验证旧端不能被误判为已协商。原消息池描述符、空闲块、锁、队列和跨CPU搬运是夹具；这次证明的是消息对象引用，**不是像素或参数银行最后引用**。

为了执行原登记表写入，`CpMachine.enable_bss_prefix`只开放锁定BSS描述符`(0x106f000,0x8a3b40,0x1197000)`下、平面镜像已包含的显式整页，预算和重复开放检查保持；页设RW/NX，保留原字节。没有开放整个BSS或CP代码写权限，也没有伪造完整启动清零。

## EVF通知与最后帧

[cp_notifications.py](../../custom-filters/a7filters/cp_notifications.py)继续执行`0x1f62b0 → 0x6a3070 → 0x6b4f00 → 0x1f9180`，在24字节通知进入序列化之前停止。原头为`0x2001/0xf002`、操作`0x39`、参数长度12。输入`0x1234`与`0x11234`实际产生相同通知，只保留低16位；未初始化的两个额外参数字以零栈夹具承接，不赋予其版本语义。

原缓冲查询`0xb2a58a`在头`0x20`时返回1，归还函数将头置为`0x80000020`后返回0，清除该标记后又返回1；同一句柄没有观察到代号字段。这里只执行标志/查询，未执行真正分配器重用、DMA结束或最后图像帧拥有者。因此不能用低16位通知、句柄或头标志直接触发`af_apply_owner_end`。
