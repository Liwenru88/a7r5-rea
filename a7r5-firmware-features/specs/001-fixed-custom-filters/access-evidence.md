## 本轮结论

32槽扩展的查找、枚举和选择分派已经有当前4.06原指令执行证据；机内持久化已追到两条不同的Backup客户端路径及其错误语义；CP已验证八项通知写入、锐度范围字段转发和双缓冲切换顺序。后续补证又新增18组场景，见[原厂通路补证](native-paths.md)。

三项整体接入门槛仍未满足。后续[界面接入批次](ui-access.md)已补原生行注册、32种选中名称呈现和目标架构八项分流；完整导航、显示快照和实际AP挂钩仍缺证。原厂LUT文件通路的启用条件、可用空间与耐久提交未证明；CP实时更新、最终消费及拍摄引用释放仍缺证。当前不能据此生成安装补丁。

本轮还纠正两处旧假设：`0x37e98c`的`+0x25`不是已证明的锐度范围下游；`0x16afd14`也不能直接认作通知状态`0x157aa10`的副本。

## T01：列表从“能查找”推进到“能有界枚举及分派”

已确认的调用关系：

```text
描述符 0x5858b08
  +0x54 条目数19，+0x58 128字节记录表
    → 0x1bcf3fc 枚举可见菜单身份，遵守调用者给定的输出容量
    → 0x1bd9180 由菜单身份查找行+0x34选择值
    → 0x1bd924c 查找并尾调描述符+0x80的setter
    → 0x1c6f208 写属性0x690，再通知0x252ca34
```

- 原厂枚举器`0x1bcf3fc`执行7组场景：原表19行、候选33行，容量0/1/18/32/33，以及特殊项隐藏。结果数量、顺序和输出前后保护区均符合预期。描述符获取和可见性判断由夹具提供，未执行原厂隐藏规则。
- 完整选择分派函数`0x1bd924c`执行34次：候选33行逐项命中、一次未命中。命中时准确向setter传递行`+0x34`，未命中不调用setter。页面门控、注册表查询和setter边界为夹具，未实际写模型。
- 主选择页`0xd9`工厂通过`0x1b4860c`的type1分派到`0x1b47474`。该函数按页面索引在全局区选取48字节控制对象，不按外观条目数分配对象。它不能证明行呈现器容量。
- 共享枚举调用点如`0x220fb24…0x220fb48`、`0x2210378…0x22103bc`提供1024字节、256个身份的缓冲。它证明这些调用点的局部空间大于33项，不能推广为所有创意外观入口都已支持32槽。
- 另有全局扁平菜单缓存写入窗口`0x1bd9eb0…0x1bd9f00`。指针`0x595df20 → 0x74dc998`、`0x598b6c0 → 0x74e2ea8`与后续计数区的相邻跨度均为`0x6510`。后续原指令验证证明：保持本描述符类别标志和父项时走`0x1bd9d9c`，19/33/82行均只追加一个父项记录；不再将这一分支按33行计额外占用。其他缓存和呈现器仍须独立验证。

具体待改清单：33条记录及两处描述符注册引用、行身份到20用户槽的独立路由、原厂18项参数数组访问、调参页`0x3b7`、名称获取/刷新、全局可见项缓存、导航和特殊项。候选测试使用的`0x100000…`只是夹具ID，未注册到固件，不能直接进入实际菜单表。

## T02：保存不能复用“返回成功”的表象

### 同步Backup客户端

`AP 0x35b88d8 → Backup_write → libbackup 0x1ff0 → backup_sync_msg 0x1a10 → osal_snd_sync_msg`。

真实库代码在消息中使用目标`0x3e014d`，write操作码9、write_vsize操作码10、sync_subsystem操作码15。变参打包器写入子系统、记录身份、数据指针以及可变长度；没有找到“创建任意记录”的协议证据。

执行7组场景：正常写、服务端错误、消息分配失败、传输失败、可变长度写、正常同步、同步错误。分配/传输/回复由夹具提供，消息格式与释放路径执行原代码。分配或传输失败时，外层Backup API返回初始错误`-1`；服务端错误通过回复状态返回。

尤其需要区分：`backup_sync_msg`本身在退出时返回0，外层API从输出状态变量取得真实结果。不能使用底层助手的返回值判定业务成功。

### AP原厂同步包装器丢失错误状态

`0x35b8908`调用`Backup_sync_subsystem(0x2cf)`后，尾调`0x3694648`。后者首先把`w0`改成日志事件值`0x32`，再执行日志函数，没有保留同步状态。

执行3组组合：同步结果0/-7、日志结果0/-9。包装器最后返回日志夹具的结果；同步失败`-7`可以被覆盖为0。**该包装器不能直接作为新槽位保存的成功回执。**这里不是相机发生了保存失败，而是离线注入错误后验证了原指令的传播行为。

### BackupManager路径也没有完成耐久写入

同包`libBackupManager.so`的`0x135c`先调用`Backup_get_datasize(id)`；长度查询失败就拒绝转发。长度有效时调用`BkDmn_write`，后者`0x128c`经`osal_snd_msg`异步入队。其正常返回值为记录长度，而非通用的0成功状态。

执行3组场景：查询失败、已有9字节记录入队成功、入队失败。它们只验证记录查询和错误/返回语义，不执行后台写入，也不证明可以新增Backup身份。

新存储适配器必须保留写入/同步原始状态，取得明确完成条件并回读；持久化前不得调用`af_finish_save(...,1)`。不能把`write_vsize`当作创建新记录、把异步入队当作落盘、或把同步包装器返回0当作耐久性证明。

具体待补：同步服务端的处理函数及记录定义、可新增的私有记录或独立文件区、启动读取入口、空间预算、文件/目录同步与恢复顺序。历史`/setting`可写挂载不替代这些证据；本轮没有选择或写入机内路径。

后续已定位原厂LUT文件区的条件挂载与写入器：`0x3691384`未保留fsync/close错误；`/dev/nflasha30 → /usr/data/lut`由功能谓词门控，本包目录缺失。详见补证，不将该设备认作可用自定义区。独立`af_record`封装和双副本选择已实现，不代表实际文件写入及耐久恢复。

## T03：字段转发与拍摄版本必须分开证明

### 已执行的字段链

八个通知接收器分别从消息`+8`读取值，写入`0x157aa10`对应字段。每个接收器均在当前CP原指令上执行，验证返回1且仅修改目标字节。日志开关由夹具关闭。

锐度/锐度范围的派生窗口：

```text
指定源状态+0xd2e/+0xd2f
  → 0x905430…0x905442 → 派生参数+0x24/+0x25
  → 调用点0x9073ca…0x9073d6：r1和r3传递r6派生上下文
  → 0x92e372入口r5=r1
  → 0x92e6a0…0x92e6ac → 下游结构+0x35c/+0x35d
```

1～5五档均执行两个复制窗口并比对输出。源状态/派生上下文指针由夹具指定，不能据此声明真实取景/JPG已使用该状态，更不能声明已经找到最终锐度计算器。

### 已校正的错误串链

`0x9073b6`调用`0x37e5a8`时，`r1=另一结构+0x470`，`r2=r6`。函数将r1保存在r5；`0x37e870`/`0x37e8ae`还会将该结构`+0x25`写成1/0。因此`0x37e98c`读取的`[r5,+0x25]`不能接在锐度范围副本后面。上一轮“两级锐度范围副本”的表述撤回。

`0xd0f3bc`记录表还明确包含`(0x02a40000, 0x016afd14, 0x1200)`。尚未建立它与通知状态的别名/更新关系，设计中不再直接称`0x16afd14`为通知状态的成像副本。

### 双缓冲已有切换证据，但没有帧释放证据

`0x907250`根据索引字节`0x19c98b2`的反值，选择`0x1f52cf8 + index * 0x1270`，调用参数构造器，随后翻转索引，最后调用完成回调。两种初始索引均已执行，缓冲选择和事件顺序符合原代码。

参数构造器及完成回调是明确替代边界。验证只证明“构造器返回后切换索引再回调”，**未证明回调等于照片帧释放**；这里也未发现局部引用计数检查。不能把该双缓冲直接当作可安全复用动态LUT载荷的逐帧版本协议。

后续补证已执行`通知状态0x157aa10 → master 0x164eef0 → 快照0x1653c68 → 上下文0x192b070 → 0x157c278`的真实复制和构造链，连接到上述字段转发；该来源复制的已知调用者属于初始化。具体仍待补：后续实时状态更新、取景和JPG各自的消费条件、拍摄锁定点、完成回调后参数/色表/曲线是否仍被引用，以及缓冲复用条件。
