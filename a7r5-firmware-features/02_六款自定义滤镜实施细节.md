## 2. AP：选择、默认值与名称

4.05只有ST基底才发送新编号，用户旧槽基底0／5／6／7／4／8使五槽回到FL／IN／SH／VV2／BW。4.06在`0x3550354`转换函数中按主选择10～15直接发送249～254；无需写个人Backup。原生FL、IN等仍在原生入口可选。

这六槽现在是固定滤镜槽：更改旧基底不会改变滤镜身份。调节滑块及其保存函数未修改，旧的滑块值仍影响结果，不能把非默认设置的照片当成参数校准基准。

默认表`0x4a422f8`的三组各18条记录，索引10～15设为0。显示名getter`0x1bc78a4`进入助手`0x500fbc0`，查询虚方法偏移`0x8d0`。最终仅将`0x500fbd8`的`cbnz w0,0x500fbf8`替换为NOP，保留查询调用和六槽ID范围检查；非六槽仍走原名称表。六个名称槽ID是`0x858..0x85d`，不要与主选择10～15或CP编号249～254混淆。

见[最终AP修复](materials/source/analysis/ap-look-selfcontained-20261022-01/ap_patch.py)与[早期六槽AP实现](materials/source/analysis/custom-features-20261021-03/research-materials-v3/code/ap_runtime.py)。早期文件保留Eterna且仍要求ST，它是历史实现参考，不能作为最终入口直接运行。

## 3. UXC菜单资源怎样修改

修改`nflasha15`内`/share/app/string_<language>_horizontal.uxc`和`_vertical.uxc`，共34语言×2方向。不是所有`string_*.uxc`；基础、`_f`、`_g`、`func_j`资源仍存在且不应计入68份方向资源。

当前源格式门槛：group5、3032条记录、data_base6080。生成过程：

1. 在原数据区起点插入12字节索引空间，使data_base变为6092；保留原有记录相对位置。
2. 文件偏移12的组合计数字段更新为`3038 | (3038 << 12)`。
3. 在索引表`16+2*(3032+i)`写入新增记录相对新data_base的4字节单位偏移；该u16不能溢出。
4. 尾部追加`u32(0x1e000000 | ((名称ID)&0xffffff))`、UTF-8名称、NUL，再补齐4字节对齐。
5. 原版实现先加入Eterna，后将其8字节记录改成`Astia\0\0\0`；本材料直接生成Astia，并以68份最终摘要证明结果逐字节相同。

每份资源增长132字节，总增长8976字节。原有索引与文字内容必须全部回读保持。只用字符串搜索直接覆盖长短不同名称，会破坏偏移或邻近记录。

算法见[name_resources.py](materials/source/analysis/custom-features-20261021-03/research-materials-v3/code/name_resources.py)及[menu_names.py](materials/source/analysis/joint-look-adaptation-20261022-01/menu_names.py)。原源码路径依赖保留供审阅，运行复现用统一入口。

## 4. CP原生色表格式与上传路径

每槽1215字节，`5×9×9×3`，三通道平面排列、有符号字节，有效七位范围−64～63。不是1215个浮点RGB三元组，也不是可直接拷入CP的DCP文件。

六表前有32字节头：`magic=0x364c3741`、`version=0x00010006`及六个FNV-1a32摘要。FNV初始2166136261、每字节异或后乘16777619并截断32位。各表的尺寸／范围／摘要都应检查；错误表不应用。

表头和六表位于CP文件`0x108d080+576=0x108d2c0`起；固定代码读取对应标记并交给原厂打包／上传路径。主要控制窗口包括VA`0x230da8`、打包路径`0x231654`、上传`0x414f44`和查询`0x415160`。原始helper位于VA`0xbef4c0`附近，最新参数包装器另见后述布局。

原厂打包顺序表在CP文件`0xd841d8`，405个索引必须为0～404的排列。某强度level1～8下，每平面值按`(value*level)>>3`缩放，再将三通道七位值按位22／12／2打包为u32，总1620字节。符号、算术右移与排列顺序均影响结果，不能把原1215字节直接当上传缓冲。

AP标记必须在CP原参数上下文中保留；只在需要ST原生路由的输出参数副本中归为ST，不能把全局源标记清零，否则后续联合参数无法知道选择哪一款。

## 5. 联合曲线／矩阵／色度

每个`.a7look`除表外还包含`native_photo.runtime_basis`：三个tone_q10、三端点各6个矩阵系数、三端点各8个色度系数。每槽共54个int16，即108字节；六槽共648字节。数值须为整数，范围−1024～1024；来源target是ILCE-7CM2／2.01，不把它当A7R5绝对校准。

矩阵六参数增量展开成：

```text
[ a+b, -a,  -b ]
[ -c,  c+d, -d ]
[ -e,  -f,  e+f ]
```

三端点各行和为0，作为增量加到本机原厂输出，不替换本机整份校准。单个矩阵可能在两款间相同；滤镜差异来自色表、曲线、矩阵、色度的组合，不能要求每个分量都不同。

包装器先执行原厂函数，再在目标照片profile0且上下文标记249～254时应用本槽增量：矩阵VA`0x71e41e`，主色度／CC1`0x71e670`，第二域`0x71e9c8`。应保留原函数ABI、校准、非目标行为和输出范围。

Gamma保留已有51行（原厂47行＋FL2／FL3新增4行），再按每槽两个ST域追加12行，编号51～62，每行7个指针。不要把FL3视频原行50覆盖掉。主／局部Gamma参数入口分别`0xaa81ca`、`0xaa8688`；曲线消费`0x41363c`。新行从原行0／10保留完整域与每列指针，不是所有列指向同一曲线。

曲线为129个u32和附属元数据组成的576字节记录。对各点y，令`x=floor((y<<12)/top)`、`v=4096-x`，按原汇编运算次序逐次右移，叠加gain、toe、shoulder并裁剪0～0x3ffff；检查单调性并同步终点字段。不能先用浮点合并所有乘法再一次取整，也不能逐曲线归一化抹掉gain。

完整运算见[look_joint.py](materials/source/a7r5-qemu/tools/look_joint.py)和[look-joint.S](materials/source/a7r5-qemu/source/guest/look-joint.S)。

| 内容 | 最终位置 |
|---|---|
| 联合数据目标 | `0x1a39450`，5872字节 |
| 六槽108字节参数 | 目标起点的前648字节 |
| 63行Gamma副本 | `0x1a396d8` |
| 四档FL2／FL3矩阵 | `0x1a3a000` |
| 搬迁的两条原曲线 | `0x1a39dbc`、`0x1a3a900` |
| 暂存源 | VA`0x11d3000` |
| 已加载联合包装器 | VA`0xbef700`起，实际742字节 |
| 引导复制窗口 | VA`0x108f40`，124字节；文件`0x524`进入 |

两条原曲线从`0xbef700`和`0xbef940`搬走，修正所有已确认Gamma引用，腾出1152字节已加载空间放包装器。不能仅把曲线数据写到文件尾，假定它会自动映射到运行地址；复制器需验证载荷FNV、处理重复调用并擦除暂存。原data描述符、全局变量地址、页表与栈位置保持。

最终配方同时包含这些步骤。删除某一跳转、复制器或Gamma引用，可能使菜单正常而取景不变，甚至影响启动。完整外部加载链仍未验证，不扩大到“已经模拟全部相机硬件”。

## 可直接执行的离线复现步骤

以下命令面向macOS／Linux的bash或zsh。材料中的Python组件工具没有硬编码本机路径，但本轮只在macOS arm64验证；Windows命令行没有验收。

**此入口复现当前整合4.06，包含四项功能，不是仅修改本文一项。** 四份文档按研究主题拆分，共享CP包装器、Gamma、加载和AP代码，不能把四份不同CP二进制相互覆盖。只有NTSC文档另提供经过校验的独立AP组合。

### 第一步：准备输入和运行环境

需要Python3.12及以上、`uv`，以及有合法使用权的原厂A7R5 4.00 DAT。把路径替换成自己的真实路径；保留引号。

```sh
KIT="/path/to/a7r5-firmware-features文档-20261023"
OFFICIAL="/path/to/official-4.00/BODYDATA.DAT"
RUN="$KIT/work-$(date +%Y%m%d-%H%M%S)"
mkdir "$RUN"
uv venv "$RUN/venv" --python 3.14
uv pip install --python "$RUN/venv/bin/python" -r "$KIT/materials/dattool/requirements.txt"
PY="$RUN/venv/bin/python"
```

依赖版本已固定：numpy2.5.4、pycryptodomex3.24.1、cryptography50.0.2。不要修改系统Python或拿其他机型固件尝试这些偏移。

原厂DAT必须满足：

```text
长度：754525608字节
SHA-256：51e1176a255a9a4b4782dfbcfa6c5f332b71173bdfe9ed2bcf4fca6bcbc6c2e2
机型：ILCE-7RM5，明文机型字段0x11030080
版本：原厂4.00
```

### 第二步：完整验证原厂包，解包到全新工作副本

```sh
"$PY" "$KIT/materials/dattool/dattool.py" verify "$OFFICIAL" > "$RUN/original-verify.json"
"$PY" "$KIT/materials/dattool/dattool.py" unpack "$OFFICIAL" --output "$RUN/work" > "$RUN/unpack.json"
```

`verify`验证全部帧；不能用只读首帧的`inspect`代替。新工作目录需要约1GiB，打包还需要至少3GiB空闲临时空间。解包器不在主机展开归档中的符号链接，只在清单保存链接信息。

### 第三步：修改工作副本中的组件

```sh
"$PY" "$KIT/materials/reproduce.py" \
  --workspace "$RUN/work" --feature all \
  --receipt "$RUN/components-applied.json" > "$RUN/components.log"
```

执行前会检查原厂DAT来源、所有AP／CP／UXC／WBI文件的完整SHA-256和补丁前像；先生成全部目标，再替换工作副本。原始DAT不会被打开写入。

本步骤修改：

- `components/usr/lib/appFw.so`：最终AP，97368304字节。
- `components/cpapp-b.bin`：最终CP，17617008字节。
- `components/usr/share/app/string_*_horizontal.uxc`及`_vertical.uxc`：68份资源，各增长132字节。
- `archive/0700_part_image/dev/nflasha5`：只改偏移3，WBI2→WBI3。此标记不证明实际冷启动、NOR或CP已重新加载。

回执必须为`WORKSPACE_COMPONENTS_VERIFIED`。新AP／CP必须分别为：

```text
AP d15933ceb5ff9ad0b4f789cbabd6ff0a51526472dd35c90db97196dd227820e9
CP 18b265c589eb4201d3b3680857d897b693d06c6dd491d795dbb3a616d6182e97
```

脚本拒绝已经修改过的前像，不能在同一个work目录重复执行。若替换工作文件中途失败，目录可能部分修改；不要继续打包，也不要修改摘要门槛“强行通过”，应从原厂DAT另建全新work重做。没有自动机身恢复或自动刷写动作。

### 第四步：用与机身信任相配对的研究身份打包

```sh
KEY="/private/path/research-signing-private.pem"
PUBLIC="$KIT/materials/dattool/keys/research-public.pem"
"$PY" "$KIT/materials/dattool/dattool.py" pack "$RUN/work" \
  --output "$RUN/BODYDATA.DAT" --version 4.06 \
  --private-key "$KEY" --public-key "$PUBLIC" > "$RUN/pack.json"
"$PY" "$KIT/materials/dattool/dattool.py" verify "$RUN/BODYDATA.DAT" \
  --public-key "$PUBLIC" > "$RUN/final-verify.json"
```

`KEY`必须是RSA-2048配对私钥，在macOS／Linux上权限为0600。**材料未附私钥；没有配对私钥则不能完成这条打包路径。** 原项目已有本机私钥或先前独立工具包中的私钥，需要所有者单独保管和交付。不要将私钥写进Markdown、命令参数字符串或公开仓库。

本材料配套研究公钥PEM SHA-256为：`7f65b296987df665da217de514e785f75238e686ddd18952fa425fc47e8c858a`。不是索尼官方公钥，也不是索尼私钥。若使用自己的身份，需要使用匹配公钥，并另行解决机身信任；这四份功能文档不提供信任环境写入方案。

打包器合并组件到分区，更新对应归档`.sum`中的CRC32，更新BCD版本头与头CRC，再加密、签名和完整回读。不手改`manifest.json`、`.sum`、文件系统分配或签名字段；不要同时修改同一分区的原始镜像与其内部组件。

`4.06`是本次研究版本示例，不是官方4.06。相同／更高版本机身是否接纳未由此证明；不要自行加入同版本绕过。打包器选择的空闲块分配次序可能不同于历史构建，因此**目标组件摘要应完全一致，整份DAT摘要不强求等于历史文件**；最终以本次完整回读回执绑定输出。

### 第五步：完成验收后才讨论上机

`final-verify.json`必须有签名通过、`full_frame_validation=true`、正确机型和研究版本。该校验不等于机身更新器接纳、完整启动或实拍成功。

本手册的自动步骤到此结束，不操作USB／SSH／SD卡。若后续决定实机试验，必须另行核对当前机型、固件、更新器信任、版本准入、供电及恢复条件，再由操作者通过原厂菜单完成。完整DAT可能重写分区，不能把“改了几个字节”理解为机身只写几个字节；旧DAT也不自动等同可用救援包。

## 本功能的验收与已知限制

离线依次确认：六个主选择发送249～254；旧基底为FL／IN等时名称仍正确；UXC68份精确回读；每表FNV、七位符号和打包顺序正确；复制器实际执行；原厂参数输出加对应增量，非目标和已有51行Gamma的参数内容不变（必要的地址重定位另行核对）。

实机另验：六款名称、基底不再需要手改、取景／新JPEG／ARW参数变化、滑块保持及静音／原生外观不回归。先控制曝光和白平衡，再比较颜色，不把软件参考渲染当成相机ISP证据。

**视频限制：** 本轮修复AP视频状态编号，但现有联合增量针对照片参数profile0；视频profile21矩阵沿原包行为。色表或部分Gamma路由存在，不等于照片整套联合参数都已用于视频。不得对外宣称六款完整视频成像已通过。
